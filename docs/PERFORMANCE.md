# 性能验证记录

## 结论

在本机 MySQL 8.0.34 空库上执行 100 个用户、20 并发的同一商品下单测试，100 个请求全部成功，最终库存为 0，未出现超卖。

| 指标 | 结果 |
| --- | ---: |
| 成功 / 失败 | 100 / 0 |
| 总耗时 | 1,025 ms |
| 吞吐量 | 97.56 orders/s |
| 平均响应时间 | 189 ms |
| P50 | 185 ms |
| P95 | 257 ms |
| P99 | 294 ms |
| 最终库存 | 0 |

## 测试条件

- 日期：2026-08-26
- 应用：Java 17.0.16、Spring Boot 3.5.16，默认 HikariCP 配置
- 数据库：MySQL Community Server 8.0.34，本机独立实例
- 机器：AMD Ryzen 7 7840H（8 核 16 线程）、15.2 GB 内存、Windows
- 场景：预先注册用户并加入购物车，计时阶段仅包含 100 次结算请求；所有请求争抢同一个库存为 100 的商品
- 工具：仓库内 `tools/CheckoutLoadTest.java`，使用 JDK 自带 `HttpClient`

该结果是开发机上的可复现实验，不等同于生产容量承诺。热点商品使用数据库行锁会串行化库存写入，真实大促场景需要进一步做队列削峰或原子库存更新。

## 复现方法

先使用 MySQL 配置启动应用，再在 PowerShell 中执行：

```powershell
.\scripts\run-load-test.ps1 http://127.0.0.1:8080 100 20
```

压测器会自动创建测试商品、用户和购物车，随后并发提交订单；只要存在失败请求或最终库存不为 0，进程就会以失败状态退出。

## 压测发现并修复的问题

第一次 MySQL 压测只有 11/100 个请求成功。原因是购物车关联提前加载了商品实体，等待悲观锁后仍持有旧的 `@Version`，提交时触发乐观锁冲突。结算逻辑改为在获得 `PESSIMISTIC_WRITE` 锁时同步刷新商品实体，重新测试后达到 100/100 成功。这个问题在 H2 并发测试中没有稳定复现，因此保留 MySQL 实测作为补充验证。
