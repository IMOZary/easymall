# 技术设计说明

## 架构

EasyMall 采用按业务域组织的单体架构，包含 `user`、`catalog`、`cart`、`coupon`、`order` 和 `admin` 六个主要模块。请求通过 Controller 进入应用，Service 负责业务规则与事务边界，Repository 负责数据访问。

前端静态资源由 Spring Boot 一并发布，通过 REST API 与后端交互。默认数据源为文件型 H2，MySQL 配置用于完整环境运行；两种数据库使用同一组 Flyway 迁移脚本。

## 库存一致性

结算事务按商品 ID 排序后，使用 `PESSIMISTIC_WRITE` 锁定商品记录。获得锁时同步刷新商品实体，确保 Hibernate `@Version` 与数据库当前版本一致，然后完成库存校验和扣减。

固定加锁顺序用于降低多商品订单相互等待形成死锁的概率。热点商品的写入仍会发生锁等待，因此当前方案适用于常规交易流量；更高并发场景可进一步采用带库存条件的原子更新、库存令牌或消息队列削峰。

## 重复下单处理

每次结算请求必须携带 `idempotencyKey`。前端在打开结算页面时生成 key，并在失败重试时持续复用；只有订单成功或购物车内容变化后才清除。提交期间按钮保持禁用，避免连续点击产生并发请求。

服务端先锁定用户记录，将同一用户的“查询幂等键、消费购物车、创建订单”串行化，然后按用户和幂等键查询历史订单，命中后直接返回已有结果。数据库仍使用 `(user_id, idempotency_key)` 联合唯一约束作为最终保护。

## 订单状态与补偿

订单状态按照以下路径流转：

```text
待支付 → 已支付 → 已发货 → 已完成
   └──────────────→ 已取消
```

支付、取消、发货和超时关闭都会先锁定订单记录，避免多个操作同时修改状态。待支付订单超过 30 分钟后由定时任务批量关闭，并在同一事务内回补库存、销量和优惠券使用次数。

## 商品快照

订单项保存下单时的商品名称、图标、单价、数量和小计。商品后续改名或调价不会改变历史订单，订单金额也不依赖商品表的当前数据。

## 认证与权限

应用使用 Spring Security、BCrypt 和服务端 Session 完成认证。普通用户可以管理自己的购物车和订单，管理员可以访问经营数据、商品管理及发货接口。当前是同源浏览器应用，因此没有使用 JWT。

## 数据库版本管理

Flyway 负责创建业务表、增加订单过期字段及建立查询索引，Hibernate 使用 `ddl-auto: validate` 校验实体映射，不直接修改表结构。索引设计和执行计划见 [`DATABASE.md`](DATABASE.md)。

## 当前边界

- 支付和物流使用本地状态模拟。
- 商品资源未接入对象存储。
- 未实现短信验证码、接口限流和审计日志。
- 当前性能记录来自单机环境，不代表生产容量。

## 关键代码

1. `order/OrderService.java`：结算事务、行锁、状态流转和补偿。
2. `order/OrderRepository.java`：订单行锁与超时扫描查询。
3. `order/ShopOrder.java`：订单模型和幂等联合唯一约束。
4. `order/OversellConcurrencyTest.java`：并发防超卖测试。
5. `config/SecurityConfig.java`：认证入口和角色权限边界。
