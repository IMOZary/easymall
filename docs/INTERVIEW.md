# 简历描述与面试准备

## 项目名称

EasyMall 单体电商系统（Java / Spring Boot）

## 可直接用于简历的项目描述

> 独立设计并实现基于 Java 17、Spring Boot、Spring Security 与 JPA 的单体电商系统，完成用户认证、商品检索、购物车、优惠券、订单结算、超时关单、支付/发货状态流转及运营后台等核心业务，并提供 H2 零配置演示与 MySQL 容器化运行方式。

推荐亮点条目：

- 使用数据库悲观行锁实现库存校验与原子扣减，并按商品 ID 固定加锁顺序降低死锁概率；在 MySQL 8 上完成 100 用户、20 并发热点商品下单测试，100% 成功且最终库存为 0，P95 为 257 ms。
- 通过客户端幂等键、用户维度联合唯一索引和历史订单复用机制解决重复点击/网络重试导致的重复下单问题。
- 设计订单状态机与 30 分钟超时关单任务，使用订单行锁解决支付/取消/关单竞争，并在取消事务中完成库存、销量和优惠券次数补偿。
- 使用 Flyway 管理 2 个数据库版本及 7 个业务索引，通过 `EXPLAIN ANALYZE` 验证用户订单和超时扫描命中联合索引，并配置 GitHub Actions 自动执行测试与 MySQL 启动检查。
- 对商品名称、价格和图标建立订单快照，隔离商品后续修改对历史订单的影响；使用 BCrypt + Session RBAC 完成普通用户与管理员权限控制。

不要全部堆进简历。根据版面选项目描述 + 3 条亮点即可。

## 3 分钟项目介绍

“这是我独立完成的一个 Java 单体电商项目。我的目标不是堆微服务组件，而是把电商最核心的业务闭环做完整，并保证几个关键一致性问题可以讲清楚。

用户端支持注册登录、商品搜索分类、购物车、优惠码结算和订单中心；管理端可以看经营指标、管理商品并给已支付订单发货。默认 H2 一条命令就能演示，也可以切换 MySQL。

我重点处理了三个问题。第一是库存超卖：下单事务对商品行加悲观写锁，校验后扣库存，多商品按 ID 排序加锁，并用并发测试验证。第二是重复下单：前端每次结算生成幂等键，服务端先查历史订单，数据库再用用户和幂等键联合唯一约束兜底。第三是状态一致性：订单采用显式状态机，取消时在同一事务回补库存并释放优惠次数。

在架构上我选择按业务域组织的单体应用，因为项目规模不需要微服务。这个选择让我能把重点放在事务边界、数据建模和可测试性上。”

## 高频追问

### 为什么用悲观锁，不用 Redis 分布式锁？

当前应用是单体且所有库存写入都落到同一数据库，数据库行锁已经能提供正确性，事务边界也最清楚。Redis 锁还要处理锁过期、续期和数据库事务一致性，会增加不必要的故障点。如果未来拆成多库存服务或吞吐量明显上升，再考虑库存预扣、消息队列或 Redis 原子脚本。

### 悲观锁有什么缺点？

热点商品会出现锁等待，降低吞吐量。项目通过缩短事务、固定加锁顺序减少影响。大促场景应改为库存令牌、队列削峰或乐观更新 `stock = stock - n where stock >= n`。

### 幂等方案还有竞态吗？

“先查再插”在两个并发请求同时进入时仍可能竞态，所以数据库联合唯一索引才是最终防线。当前前端和正常重试会复用同一订单；生产环境还可以捕获唯一键冲突后用新事务查询原订单，或建立独立幂等记录表。

### 为什么订单项要保存商品快照？

商品是可变数据，历史订单是交易凭证。如果只存商品 ID，商品改名、调价或删除后，历史订单会失真。因此下单时保存名称、单价、图标和数量，并基于快照计算小计。

### 为什么没有用 JWT？

这是同域部署的浏览器商城，服务端 Session 更简单且支持主动失效，不需要处理 Token 存储和刷新。JWT 适合多客户端或跨服务传递身份，但不是所有项目的默认答案。这里更重要的是 Spring Security 的认证链和 RBAC 权限边界。

### `@Transactional` 为什么放在 Service？

一个业务操作通常跨多个 Repository，例如下单同时读取购物车、锁库存、写订单、使用优惠券并清空购物车。事务应该覆盖完整业务用例，所以放在 Service 层，而不是单个 DAO 方法。

### 项目有哪些不足？

支付和物流是模拟实现；没有验证码、限流和审计；后台商品编辑 UI 只覆盖新增，修改通过 API 支持。H2 与 MySQL 已执行迁移兼容验证，但性能数据仅来自单机开发环境。这些是有意识的范围控制，不影响简历项目展示的核心闭环。
